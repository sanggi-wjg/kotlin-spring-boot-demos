### 3.1 개요

간단한 커머스 주문 API를 구현한다. 상품 조회, 재고를 차감하는 주문 생성, 주문 취소와 재고 복원, 쿠폰 발급과 적용, 주문 목록 조회를 제공한다.

### 3.2 공통 규칙

C1. 금액

- 통화는 KRW 하나만 다룬다. `Money`는 원 단위 정수(`Long`)를 감싸는 값 객체이고 소수점을 갖지 않는다
- 정률 할인 계산 순서: 원금액에 할인율 적용 -> 최대 할인 금액 상한 적용 -> 원 단위 버림. 상한 적용 후에 절사한다
- 최종 결제 금액의 하한은 0이다

C2. 사용자 식별

- 인증은 범위 밖이다. 모든 요청은 `X-User-Id` 헤더로 사용자를 식별한다. 헤더가 없으면 400

C3. 페이징

- `size` 기본값 20, 상한 100. 상한을 넘기면 400
- 커서 기반. 마지막 페이지에서 `nextCursor`는 null, `hasNext`는 false

C4. 멱등 키

- 적용 대상은 상태를 바꾸는 세 API: 주문 생성, 주문 취소, 쿠폰 발급
- 헤더 이름은 `Idempotency-Key`. 누락 시 400
- 보관 기간 24시간. 만료된 레코드는 일 1회 정리 배치로 삭제한다
- 같은 키에 다른 요청 바디가 오면 422로 거부한다 (요청 바디 해시를 함께 저장해 판정)

### 3.3 기능 요구사항

F1. 상품 조회

- 상품 목록 조회 (커서 페이징), 상품 단건 조회
- 응답에 상품명, 판매가, 현재 재고 수량, 판매 상태 포함
- 판매 중지 상품은 목록에서 제외하고 단건 조회는 허용한다 (주문 이력에서 진입하는 경로 때문)

F2. 주문 생성 (재고 차감 동반)

- 여러 상품을 한 주문에 담을 수 있다
- 주문 생성 시 각 상품의 재고를 주문 수량만큼 차감한다
- 쿠폰을 하나 적용할 수 있다 (선택). 쿠폰 중복 적용은 지원하지 않는다
- 최종 결제 금액은 서버가 계산한다. 클라이언트가 보낸 금액은 신뢰하지 않는다
- 외부 결제는 mock 어댑터를 호출한다

F2-1. 주문 상태와 전이

- 상태: PENDING(재고 차감 완료, 결제 미확정) / PAID / PAYMENT_FAILED / CANCELED
- 허용 전이
    - PENDING -> PAID: 결제 성공
    - PENDING -> PAYMENT_FAILED: 결제 실패 응답 수신, 재고와 쿠폰 보상 처리
    - PAID -> CANCELED: 사용자 취소, 재고와 쿠폰 보상 처리
- PENDING 주문에 대한 사용자 취소 요청은 거부한다 (결제 결과 확정 전이라 판단할 수 없다)
- 그 외 전이는 `ORDER_NOT_CANCELABLE`로 거부하고, 전이표를 테스트로 고정한다

F3. 주문 취소와 재고 복원

- PAID 상태의 주문만 취소할 수 있다. 부분 취소는 범위 밖이고 전체 취소만 지원한다
- 취소 시 차감했던 재고를 원복하고 사용한 쿠폰을 되돌린다
- 이미 취소된 주문은 다시 취소할 수 없다

F4. 쿠폰 발급과 적용

- 쿠폰 정책(정액 할인 / 정률 할인, 최소 주문 금액, 최대 할인 금액, 유효기간, 총 발급 수량)을 정의한다
- 사용자에게 쿠폰을 발급한다. 총 발급 수량을 초과할 수 없고, 같은 정책의 쿠폰은 1인 1매까지 발급한다 (정책별 제한이며 전체 보유량 제한은 없다)
- 보유 쿠폰 목록을 조회할 수 있다
- 주문 시 보유 쿠폰을 적용해 할인 금액을 산출한다

F5. 주문 조회 (커서 페이징)

- 사용자별 주문 목록을 최신순으로 페이징 조회한다
- 주문 상태로 필터링할 수 있다

### 3.4 비기능 요구사항

N1. 동시 주문 시 재고 정합성

- 동일 상품에 동시 주문이 들어와도 재고는 음수가 되지 않는다
- 재고가 100개일 때 동시 100건의 1개 주문은 정확히 100건이 성공하고 최종 재고는 0이다

N2. 중복 주문 방지

- 클라이언트 재시도나 더블 클릭으로 같은 주문이 두 번 생성되지 않는다
- `Idempotency-Key` 헤더로 식별하고, 같은 키의 재요청은 최초 처리 결과를 그대로 반환한다 (C4 참조)

N3. 응답 시간 목표

- 조회 API는 로컬 기준 p95 200ms 이내
- 주문 생성은 락 대기를 포함해 p95 500ms 이내
- 측정 조건을 고정한다: 로컬 단일 인스턴스, 부하 도구는 k6 또는 hey, 동시 사용자 50, 워밍업 30초 후 60초 측정, 상품 100건과 재고 충분 상태
- 목표 자체보다 "무엇을 어떤 조건에서 측정했는지"를 README에 남긴다

N4. 장애 격리

- 외부 결제 mock이 실패 응답을 주면 재고와 쿠폰을 보상 처리해 원복한다
- 응답 미수신(타임아웃)은 결과를 알 수 없으므로 즉시 원복하지 않는다. 주문을 PENDING으로 유지하고 결제 결과를 재확인해 PAID 또는 보상 중 하나로 확정한다. 확정 전까지 재고가 차감된 채 남는 것은 의도된 동작이며, 그 판단 근거를 README에 적는다
- 미확정 주문이 무한정 남지 않도록 재확인 주기(예: 1분 간격)와 포기 기준(예: 10분 후 보상 처리)을 정한다

### 3.5 제약

- 언어/프레임워크: Kotlin 2.x, Spring Boot 3.4, JPA
- DB: MySQL 8.x (docker compose로 기동)
- Redis: 선택. 락 전략 프로퍼티가 `distributed`가 아니면 Redis 빈을 등록하지 않아 Redis 없이도 애플리케이션이 뜬다 (`@ConditionalOnProperty`)
- 외부 결제: 실제 PG 연동 없이 mock 어댑터. 성공/실패/지연/응답 미수신을 시뮬레이션할 수 있게 만든다
- 인증: 범위 밖 (C2)
- 프론트엔드 없음. API만 제공한다

### 3.6 기능별 엣지케이스

F1 상품 조회

- 존재하지 않는 상품 ID -> 404
- 판매 중지 상품: 목록 제외, 단건 조회 허용 (F1 정책)
- 재고 0인 상품은 목록에 노출하되 `soldOut` 플래그를 내린다
- `size`가 상한(100) 초과 -> 400

F2 주문 생성

- 재고보다 많은 수량 주문 -> 409 `OUT_OF_STOCK`
- 수량 0 또는 음수 -> 400
- 같은 상품을 라인 아이템으로 두 번 담은 경우 -> 수량 합산
- 존재하지 않는 상품 ID 포함 -> 404
- 여러 상품 중 하나만 재고 부족 -> 전체 주문 실패 (부분 성공 금지)
- 최소 주문 금액 미달 쿠폰 적용 -> 409
- 만료된 쿠폰, 이미 사용한 쿠폰, 타인의 쿠폰 -> 409
- 할인 금액이 주문 금액을 초과 -> 최종 금액 0으로 절삭
- 정률 할인의 절사: 상한 적용 후 원 단위 버림 (C1)
- 결제 mock 실패 -> 재고와 쿠폰 보상 처리
- 결제 mock 응답 미수신 -> PENDING 유지 후 결과 재확인 (N4)
- `Idempotency-Key` 누락 -> 400, 같은 키에 다른 바디 -> 422, 같은 키에 같은 바디이고 처리 완료 -> 최초 응답 재반환, 처리 중 -> 409

F3 주문 취소

- 이미 취소된 주문 재취소 -> 409 `ORDER_NOT_CANCELABLE`
- PENDING 주문 취소 시도 -> 409 (F2-1)
- 존재하지 않는 주문 -> 404
- 타인의 주문 취소 시도 -> 404 (존재 여부를 노출하지 않는다)
- 취소 동시 요청 2건 -> 한 건만 성공하고 재고는 1회만 복원된다
- 재고 복원 시 상품이 판매 중지 상태여도 재고는 복원한다
- 되돌린 쿠폰이 이미 만료된 경우 -> 사용 상태만 해제하고 만료 상태는 유지한다 (재사용 불가). 복원 결과를 응답에 표시한다

F4 쿠폰

- 총 발급 수량 소진 후 발급 요청 -> 409
- 동시 발급 요청이 수량을 초과하는 경우 -> 초과분만 실패
- 동일 사용자의 같은 정책 중복 발급 시도 -> 409
- 유효기간 경계: 시작 시각 포함, 종료 시각 미포함 (반열린 구간)
- 정률 할인에서 최대 할인 금액 상한 적용

F5 주문 조회

- 빈 목록 -> `items: []`, `nextCursor: null`, `hasNext: false`
- 커서가 디코딩 불가능한 값 -> 400
- 조회 중 새 주문이 생겨 페이지가 밀리는 경우 -> 커서 기반이라 영향 없음
