> 모듈: `basics`
>
> 코루틴도 멀티스레드 위에서 돌기 때문에 동시성 버그가 그대로 생긴다. 스레드를 막지 않는 도구(Mutex, Semaphore, Channel)를 쓸 수 있다는 점이 다르다. 이 Part에서는 이 도구들이 무엇을 어디까지 해결하는지 확인한다.

## 2-1. 코루틴에서도 race condition은 생긴다 `핵심`

**목표**: 코루틴에서 race condition을 재현한다. 각 해결책이 어디까지 통하는지 확인한다.

**핵심 개념**
> 1단계 [C-1](../1-basics/c-concurrency-flow.md#c-1-공유-상태와-동시-실행-제한)에서 먼저 익힌다.

- race condition은 결과가 실행 순서나 타이밍에 따라 달라지는 버그다. 여러 실행 흐름이 같은 가변 상태에 동시에 접근하고, 그중 하나 이상이 쓰기를 할 때 생긴다.
- 동시성 버그는 원자성(연산이 중간에 끼어들 틈 없이 한 번에 일어나는가), 가시성(한 스레드가 쓴 값을 다른 스레드가 보는가), 순서(코드 순서대로 실행된 것처럼 보이는가) 문제로 나눠 볼 수 있다. 각 해결책이 이 중 무엇을 다루는지 구분해서 본다.
- 코루틴은 디스패처가 가진 스레드 위에서 실행된다. `Dispatchers.Default`는 CPU 코어 수만큼(최소 2개)의 스레드를 쓴다. 여러 스레드에서 실행되는 코루틴에는 JVM 메모리 모델 규칙이 스레드와 똑같이 적용된다.
- `runBlocking`은 호출한 스레드를 그대로 써서 코루틴을 실행한다. 디스패처를 따로 지정하지 않으면 그 안에서 띄운 자식 코루틴도 같은 스레드에서 실행된다.

**실행 전 예측**
- 코루틴 수 × 반복 횟수를 10 × 100, 100 × 1,000, 1,000 × 1,000으로 바꿔가며 `counter++` race를 재현하면, 잃어버리는 증가분의 비율은 어떻게 변할까? race가 거의 드러나지 않는 조건도 있을까?
- 같은 코드를 `Dispatchers.Default` 대신 `Dispatchers.IO`(스레드가 코어 수보다 많다)에서 돌리면 손실 비율은 커질까, 작아질까?
- `runBlocking` 단일 스레드라도 `val v = counter; delay(1); counter = v + 1`처럼 읽기와 쓰기 사이에 중단 지점이 있으면 결과는 1,000,000일까?
- `AtomicInteger`, `Mutex`, 세밀한 스레드 한정, 굵은 스레드 한정의 처리 시간 순위는 경합 정도(코루틴 수)에 따라 바뀔까?

**실험 과제**
1. 경합 조건(코루틴 수, 반복 횟수, 디스패처)을 바꿔가며 race를 재현하고 손실 비율을 기록한다.
2. 단일 스레드에서 "읽기 → 중단 → 쓰기" 코드로 race를 재현한다.
3. `AtomicInteger`, `Mutex`, 스레드 한정(세밀/굵은)으로 고치고, 경합 조건별로 처리 시간을 비교한다.

**완료 조건**
- [ ] 경합 조건별 손실 비율 표
- [ ] 단일 스레드 race 재현 테스트
- [ ] 경합 조건별 해결책의 정확성과 처리 시간 비교

**공식 문서**: [Shared mutable state and concurrency](https://kotlinlang.org/docs/shared-mutable-state-and-concurrency.html)

## 2-2. Mutex와 synchronized `핵심`

**목표**: 코루틴 안에서 `synchronized`를 쓰면 어떤 문제가 생기는지 확인한다. `Mutex`는 무엇이 다른지 비교한다.

**핵심 개념**
> 1단계 [C-1](../1-basics/c-concurrency-flow.md#c-1-공유-상태와-동시-실행-제한)에서 먼저 익힌다.

- `synchronized`(모니터 락)와 `ReentrantLock`은 락의 소유자가 **스레드**다. 락을 얻은 스레드가 직접 풀어야 한다.
- 코루틴은 중단 지점(suspend 함수 호출)에서 멈췄다가, 재개될 때 멈추기 전과 다른 스레드에서 실행될 수 있다(Part 1).
- 재진입(reentrancy)은 이미 락을 가진 주체가 같은 락을 다시 얻을 수 있는 성질이다. Java의 `synchronized`와 `ReentrantLock`은 재진입이 가능하다.
- `Mutex`는 `kotlinx.coroutines.sync` 패키지에 있는 코루틴용 락이다. 보통 `withLock { }`으로 임계 구역을 감싸서 쓴다.
- 락을 기다리는 스레드가 어떤 상태인지는 0-3에서 쓴 스레드 덤프로 판정한다.

**실행 전 예측**
- 코루틴 1,000개가 `Dispatchers.Default`에서 같은 `Mutex`를 기다리는 순간 스레드 덤프를 뜨면, `DefaultDispatcher-worker` 스레드들은 어떤 상태로 몇 개 보일까? 같은 상황을 `synchronized`로 만들면?
- 임계 구역 안에서 10ms를 기다리는 코루틴 100개가 있다. `Mutex` + `delay(10)`과 `synchronized` + `Thread.sleep(10)`의 총 소요 시간은 각각 얼마일까? 그동안 같은 디스패처의 다른 코루틴(예: 1ms마다 카운터를 올리는 코루틴)은 얼마나 진행될까?
- 먼저 기다리기 시작한 코루틴이 먼저 `Mutex`를 얻을까? `synchronized`는 그 순서를 보장할까?

**실험 과제**
1. 위 두 번째 예측의 시나리오를 `Mutex`와 `synchronized`로 각각 구현한다. 총 소요 시간과 옆 코루틴의 진행량을 잰다.
2. 락을 기다리는 동안 스레드 덤프를 떠서 두 방식의 스레드 상태와 개수를 비교한다(0-3).
3. 대기 순서를 기록하는 테스트로 두 방식의 공정성(fairness)을 확인한다.

**완료 조건**
- [ ] "락을 기다리는 동안 스레드를 점유하는가"를 스레드 덤프 근거로 정리
- [ ] 소요 시간과 옆 코루틴 진행량 비교
- [ ] 공정성 확인 테스트

**열린 질문**

## 2-3. 동시 실행 수 제한하기 `핵심`

**목표**: "외부 API는 동시에 10개까지만 호출한다" 같은 요구사항을 구현하는 여러 방법을 비교한다.

**핵심 개념**
> 1단계 [C-1](../1-basics/c-concurrency-flow.md#c-1-공유-상태와-동시-실행-제한)에서 먼저 익힌다.

- 동시성(concurrency)은 여러 작업이 진행 중인 기간이 겹치는 것이다. 병렬성(parallelism)은 여러 작업이 같은 순간에 실제로 CPU에서 실행되는 것이다.
- `Semaphore`(`kotlinx.coroutines.sync`)는 허가(permit) N개를 나눠 주는 도구다. `withPermit { }` 블록에 들어갈 때 허가를 하나 얻고, 나올 때 돌려준다.
- `limitedParallelism(n)`은 기존 디스패처 위에 한도가 n인 view를 만든다. 무엇을 세는지는 1단계 C-1에서 봤다. 이 장에서는 블로킹 호출과 섞였을 때와 대기 비용을 확인한다.
- "동시 실행 수 제한"과 "초당 호출 수 제한(rate limit)"은 다른 요구사항이다. 외부 API 계약서에 어느 쪽이 적혀 있는지부터 확인해야 한다.
- DB 커넥션 풀(HikariCP의 `maximumPoolSize`)도 동시 실행 수를 제한하는 장치다. 4-5에서 이 장의 도구와 다시 만난다.

**실행 전 예측**
- 호출이 **블로킹**(`Thread.sleep(100)`)이라면, `Dispatchers.IO`에서 `Semaphore(10)`만 쓴 경우와 `Dispatchers.IO.limitedParallelism(10)`만 쓴 경우의 최대 동시 호출 수, 총 소요 시간, 실제로 쓰인 IO 스레드 수는 각각 얼마일까?
- 1,000건을 처리하는 두 가지 방법이 있다. `async`로 한꺼번에 띄우고 Semaphore로 제한하는 방법과, 10개씩 묶어서(chunk) 처리하는 방법이다. 총 소요 시간이 같을까?
- `Semaphore(10)` 앞에서 허가를 기다리는 코루틴이 990개일 때, 힙 메모리와 JVM 스레드 수는 기다리는 코루틴이 없을 때보다 얼마나 늘어날까?

**실험 과제**
1. 지연 100ms짜리 가짜 API를 1,000건 호출하되, 동시에 10개까지만 실행한다. Semaphore와 chunk 방식으로 각각 구현한다.
   - Channel 워커풀 방식은 2-4에서 추가한다.
2. 같은 과제를 블로킹 호출로 바꿔 Semaphore, `limitedParallelism`, 둘의 조합을 비교한다. 최대 동시 호출 수와 IO 스레드 수를 함께 기록한다.
3. 호출 지연이 들쭉날쭉한 경우(50~500ms 랜덤)에도 방식별 총 소요 시간을 비교한다.
4. 허가를 기다리는 코루틴이 많을 때의 힙 사용량과 스레드 수를 잰다.

**완료 조건**
- [ ] 논블로킹/블로킹 호출별 제한 방식 비교표(최대 동시 호출 수, 소요 시간, 스레드 수)
- [ ] 방식별 소요 시간 비교
- [ ] 대기 중인 코루틴의 비용 측정값

**열린 질문**

## 2-4. Channel: 코루틴 간 통신 `선택`

**목표**: 공유 메모리 대신 메시지 전달로 동시성을 다루는 방법을 익힌다.

**핵심 개념**
> 1단계 [C-3](../1-basics/c-concurrency-flow.md#c-3-channel과-hot-flow-선택)에서 먼저 익힌다.

- "메모리를 공유해서 통신하지 말고, 통신해서 메모리를 공유하라"(CSP 모델). 상태를 코루틴 하나에만 두고, 다른 코루틴과는 메시지로만 주고받는 방식이다.
- `Channel`은 코루틴 사이에서 값을 주고받는 통로다. `send`로 넣고 `receive`로 꺼낸다. `Channel()`을 만들 때 넘기는 capacity로 버퍼 정책(RENDEZVOUS, BUFFERED, CONFLATED, UNLIMITED)을 고른다.
- 채널에 들어간 값 하나는 소비자 **하나**에게만 전달된다. 소비자 여러 개가 같은 채널을 읽으면 값을 나눠 받는다. 이것이 fan-out 워커풀의 바탕이다.
- 채널을 닫는 것(`close`)과 취소하는 것(`cancel`)은 다른 연산이다.
- 채널은 프로세스 메모리 안의 큐다. 애플리케이션이 재시작되면 안에 남은 값은 사라진다. 유실되면 안 되는 작업은 Kafka 같은 외부 큐가 맡는다.

**실행 전 예측**
- 생산자 1개가 10ms마다 작업을 넣고, 워커 3개가 작업 하나를 50ms씩 처리한다. 버퍼가 0, 10, UNLIMITED일 때 작업 1,000개를 넣는 동안 생산자가 기다린 총 시간과 채널에 쌓인 최대 개수는 각각 얼마일까?
- 워커 하나가 처리 중 예외로 죽으면 나머지 워커와 생산자는 어떻게 될까? 워커들을 `coroutineScope`로 띄웠을 때와 `supervisorScope`로 띄웠을 때 결과가 다를까?
- 1,000건을 동시 10개로 처리할 때, 2-3의 Semaphore 방식과 Channel 워커풀(워커 10개)은 총 소요 시간과 생성되는 코루틴 수가 어떻게 다를까?

**실험 과제**
1. 첫 번째 예측의 시나리오를 버퍼 종류별(RENDEZVOUS, 크기 10, BUFFERED, UNLIMITED)로 측정한다. 생산자 대기 시간과 채널 최대 적재량을 기록한다.
2. fan-out(워커 N개)과 fan-in(결과 수집) 패턴을 구현한다.
3. 소비자가 실패하거나 취소되면 생산자는 어떻게 되는지 확인한다.
4. 2-3의 "1,000건을 동시 10개로" 문제를 Channel 워커풀로 풀고 2-3 비교표에 추가한다.

**완료 조건**
- [ ] 버퍼 종류별 생산자 대기 시간과 적재량 측정
- [ ] Channel 워커풀 구현과 2-3 비교표 갱신

**공식 문서**: [Channels](https://kotlinlang.org/docs/channels.html)
